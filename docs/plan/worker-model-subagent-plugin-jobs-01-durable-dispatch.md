# Plan — Durable detached dispatch

## Solution

Add the supervisor to the CLI seam: `task` creates a durable Job record in the per-workspace state dir and spawns the Runtime worker fully detached, returning the job id immediately; `task-worker` rehydrates and runs the loop, mirroring progress into the record and log; `status` (with `--wait`) and `logs` make Jobs observable. Nothing anywhere reaps state at session boundaries.

## Implementation Decisions

- `src/chinamax/state.py`: state root = `$CLAUDE_PLUGIN_DATA/state` when set, else `$XDG_STATE_HOME/chinamax` (default `~/.local/state/chinamax`) as a bare-CLI fallback; per-workspace dir `<repo-basename>-<sha256(realpath)[:16]>`, keyed on the workspace root — `--workspace` when given, else cwd, resolved to `git rev-parse --show-toplevel` when that succeeds (so dispatching from a subdirectory does not fragment one repo's state across several dirs), else the realpath of that directory. Files: `state.json` (derived index), `jobs/<id>.json` (full record incl. request for rehydration), `jobs/<id>.log`, `jobs/<id>.spawn.log` (worker stdout/stderr before the loop owns logging), `jobs/<id>.thread.jsonl`, `jobs/<id>.result.json` (the `result_path` runtime/01's frozen job spec requires the caller to supply), `jobs/<id>.steer/` (created empty; drained in jobs/03). This bullet is the single authoritative layout list, and jobs/02's pruning bullet defers to it by reference and enumerates all SIX per-Job artifacts — including `<id>.result.json` and the recursive `.steer/` tree — so a future addition here must be mirrored there or prune leaves orphans.
- Store invariants: per-Job records are the source of truth and `state.json` is a derived id cache — any reader that finds it missing, unparsable, or not equal to the record set rebuilds it under `state.lock` (the rebuild is a write, so it obeys the same locking discipline as every other write; an unlocked rebuild racing a mutator's record-then-index pair would put a stale index over a fresh one). The equality check compares the id SET derived from filenames, never record contents — the index exists so reads don't open every record. The scan matches the record filename strictly (`<job-id>.json`, i.e. the id pattern followed by `.json`) and NOT the bare glob `jobs/*.json`, which would swallow `<id>.result.json` and register phantom Jobs. A record that is empty or unparsable — including one caught in the window between `O_EXCL` reservation and its first publish — is skipped by the rebuild and reported as malformed, never silently dropped and never allowed to hide the healthy Jobs beside it. Mutation order is always record-then-index.
- Record mutation is one function, never ad-hoc writes: every change (dispatcher claim-of-id, worker claim, phase update, heartbeat, terminal write, and jobs/02's cancel) goes through a single updater that takes `state.lock` (`flock` on a dedicated sidecar — never on `state.json` itself, since renaming over a locked file leaves the holder locking an unlinked inode and silently voids mutual exclusion), re-reads the record, applies the change only if the record is still in the expected state, and publishes it by writing a unique tmp file in the same directory and renaming over it. Compare-and-swap rather than last-writer-wins is what stops a late heartbeat from resurrecting `running` over a terminal write, and what makes jobs/02's cancel un-outrunnable. Id uniqueness is separate and atomic: the id is reserved by `O_EXCL`-creating the record path (regenerate on collision), and every later write to it is tmp+rename.
- State dirs are created 0700 and files 0600: records hold prompt text and results. That covers the artifacts runtime/01 opens too (`transcript_path`, `result_path`) — the worker precreates them 0600 before handing the spec over, since ordinary Python creation under the default umask yields 0644. An empty or relative value for EITHER `CLAUDE_PLUGIN_DATA` or `XDG_STATE_HOME` counts as unset — a relative state root would resolve differently in the dispatcher and in the worker, which runs from a different cwd. A `--workspace` that does not exist or is not a directory is rejected before any state is created. `flock` and `/proc/<pid>/stat` make this slice Linux-only, which matches the deployment target; where `/proc/<pid>/stat` cannot be read — a non-Linux dev machine, or a child that exited before the dispatcher got to it — `pidStartTime` is written as `null` rather than failing the dispatch, leaving jobs/02 the `kill(pid, 0)` half of its liveness test.
- Schema: `schemaVersion` = 1 on every record; timestamps are ISO-8601 UTC strings; readers ignore unknown fields and default missing optional ones, and no field is ever removed or repurposed — that is what makes the schema additive (PRD user story 13).
- Job record: id `task-<base36 ms>-<6 rand>`, title/summary (prompt excerpt), profile, write flag, workspaceRoot (the RESOLVED root — the git toplevel when that resolution succeeded, not the original cwd; it is what the worker's spec pins bash to, so it must not diverge from the state-dir key), sessionId (read from the session id surface/02's SessionStart hook exports, `null` when absent; provenance and digest rendering only — no lifecycle behavior may key off it, per the jobs PRD's Further Notes, which reads that rule out of ADR 0004), status queued|running|completed|failed|cancelled, phase, pid, pidStartTime (`/proc/<pid>/stat` field 22, captured beside `pid` so jobs/02's `effective_status` can tell a live worker from a reused pid — that slice requires this slice to write it. Parse the field by splitting AFTER the last `)`: the comm field is parenthesized and may itself contain spaces and parentheses, so a naive whitespace split misreads it and would feed a wrong start-time into a kill decision), createdAt/startedAt/updatedAt/completedAt, logFile, result, errorMessage, request, schemaVersion. `request` is exactly `{prompt, profile, write, workspaceRoot, bashTimeoutSec?}` — everything the worker needs to rehydrate without seeing the dispatcher's argv.
- Terminal-status mapping: any `report_result` ends the Job as `completed` with the payload stored verbatim in `result`, including `outcome: failed` or `blocked` — the worker's self-report is the result, not a Job-level verdict (ADR 0007). Status `failed` is reserved for Runtime/worker errors and always carries `errorMessage`.
- Detach: `subprocess.Popen([sys.executable, "-P", "-m", "chinamax", "task-worker", "--job-id", id, "--state-dir", ...], cwd=<the job's state dir>, start_new_session=True, stdin=DEVNULL, stdout=stderr=<fd on jobs/<id>.spawn.log>, close_fds=True)` — new session (no controlling tty; survives parent death and terminal hangup, with the durability boundary at OS-level session cleanup such as a logind host configured `KillUserProcesses=yes`), no inherited pipes to the dispatcher. `sys.executable` is the interpreter, and `-P` plus the neutral cwd stop a workspace that happens to contain a `chinamax` module from shadowing the installed package. Immediately after `Popen` returns, the dispatcher writes the child pid (and its `pidStartTime`) onto the record, closes its own copy of the spawn-log descriptor, prints the bare job id, and exits.
- Dispatch failure path, and the ordering rule that keeps it honest: the dispatcher and the worker are two writers racing the same fresh record, so their CAS predicates must not overlap. Failures BEFORE the child exists — opening the spawn log, building argv, `Popen` itself — are caught and written as status `failed` + `errorMessage` + `completedAt`, exiting non-zero. The post-`Popen` pid write is NOT in that class: it applies only while the record is still `queued`, and a fast worker that has already claimed it (or already finished) makes that CAS fail harmlessly, so the dispatcher logs and exits 0 rather than marking a healthy running Job `failed`. Marking a Job failed because bookkeeping lost a race would strand a live worker under a terminal record.
- Recording the pid at spawn narrows, but does not close, the stranded-record window: a worker that dies after `Popen` but before claiming (import error, unreadable state) leaves a `queued` record whose recorded pid is dead, exactly the shape jobs/02's stale detector grades. The residual case is the dispatcher being killed between `Popen` and the pid write while its worker also dies before claiming — a `queued` record with no pid, which nothing probes. Two deaths inside a millisecond-scale window, called out rather than claimed away.
- Worker: `task-worker` claims its record through the locked compare-and-swap updater — `queued` → `running` + pid + pidStartTime, applied ONLY if the record is still `queued`. A failed CAS is not an error to paper over: already terminal means a cancel landed first (jobs/02 marks a not-yet-started Job cancelled directly and relies on this check, which is the whole reason a cancel cannot be outrun by the worker it was meant to stop), and already `running` means another live claimant exists — in both cases the worker exits without running rather than overwriting the record or double-executing the Job. (jobs/03 narrows the `running` arm with a reclaim: a relaunch may claim a non-terminal record whose recorded worker is PROVABLY GONE by jobs/02's shared liveness predicate; a live claimant still causes exit-without-running.) Having claimed it, the worker calls the Runtime **in-process** — building runtime/01's frozen job spec from the record (`workspace`, `profile`, `prompt`, `write`, `transcript_path` = `jobs/<id>.thread.jsonl`, `result_path` = `jobs/<id>.result.json`, `job_id`) and calling the same validated entry the `exec` verb calls, plus a reporter callback. The spec goes through runtime/01's `spec.py` validation on this path too, so a record left half-written by a crash fails with a named field rather than a confusing crash inside the loop. It never re-implements the loop and never subprocesses back into `exec`. Once jobs/02 lands its additive `seed_transcript` spec field, task-worker sets it on EVERY spec it builds, so a pre-populated transcript — a resume copy or a relaunch on a crashed Job — is seeded rather than truncated by runtime/01's fresh-run default; until then the field does not exist and the first-run transcript is empty anyway.
- `bashTimeoutSec` is recorded but NOT passed through while only runtime/01 exists — its spec rejects unknown keys. The mapping is this slice's to own, because this slice is what builds the spec: once runtime/02 lands its `bash_timeout_s` spec field, `task-worker` maps `request.bashTimeoutSec` onto it. Nothing else in the plan set claims that translation — runtime/02 declares Job lifecycle out of scope — so without this sentence `--bash-timeout-s` would be accepted, stored, and silently never affect a command.
- Reporter seam — this slice's one edit to runtime code: `loop`'s entry gains an optional `reporter: Callable[[str, str], None] | None` taking `(phase, message)`, called at every turn boundary and around each tool execution. The phase vocabulary is closed and defined here — `starting`, `calling-model`, `running-tool`, `reporting` — and is the record's `phase` value verbatim. The worker's reporter appends a timestamped line to `jobs/<id>.log`, flushed per line so `logs` and previews are never behind, and updates the record. Newlines, carriage returns, and other control characters (including ANSI escapes) are escaped so one event is always exactly one log line and a tool's raw output cannot forge log entries or rewrite a terminal rendering the preview — jobs/03 pins the same treatment for steer text. A reporter callback that raises is logged and swallowed: an observability failure must never turn otherwise valid model work into a Runtime failure.
- Record freshness: record writes are throttled to at most one per 2 s (matching the `status --wait` poll interval), and `updatedAt` is refreshed at least every 30 s even when nothing changes — the interval jobs/02's stale detector explicitly grades against, its 60 s grace being twice this; these two numbers move together or stale detection breaks. Because the loop blocks for minutes inside one API call or bash command, the heartbeat cannot be driven from the loop: a daemon thread refreshes `updatedAt` through the same locked CAS updater, and the worker stops and joins that thread BEFORE the terminal write, so a heartbeat in flight can never land after — and resurrect `running` over — a completed record. The heartbeat refreshes `updatedAt` for jobs/02's benefit only — `status --wait` deliberately does NOT wake on it, or every Job would look like it was making progress every 30 s. The terminal write (result/status/completedAt) bypasses the throttle and folds `jobs/<id>.result.json` into the record's `result`, after which the record is the authoritative copy and the file is only the Runtime's write-side artifact. Any exception escaping the loop is caught and written as status `failed` + `errorMessage` + `completedAt` before exit — and once runtime/03 lands, its structured failure payload is `errorMessage`'s source: a compact `classification/attempt_count/status_code/exception_text` rendering, with the full JSON line already in `jobs/<id>.log` via the reporter (runtime/03's failure-seam decision names this bullet as the owner of that mapping); a crash between the Runtime writing `result.json` and that terminal write leaves a readable result on an effectively-interrupted Job, which jobs/02's stale path reports honestly rather than this slice inventing a recovery.
- `status`: lists every active Job plus the 20 most recent by `updatedAt`, each Job appearing exactly once (elapsed measured from `startedAt` once running and from `createdAt` while queued, frozen at `completedAt` once terminal; phase; last 4 non-empty log lines as preview — read by seeking the log's tail rather than loading a 70-minute log whole, decoded `errors="replace"` since tool output is arbitrary bytes). `status <id-or-prefix> --wait [--timeout-ms]` snapshots `(status, phase, log size + inode)` at call start and polls every 2 s on a monotonic clock up to 240 s default, returning as soon as any differs — watching the log's size is what keeps a long single phase from going silent for the whole window, and it is O(1) per poll where recounting lines would rescan a growing file every 2 s. An already-terminal Job returns immediately.
- Exit codes, which surface/01 has the Bridge branch on instead of parsing prose: 0 = Job is in a terminal state, 2 = Job is still active, 1 = usage or resolution error. Code 2 covers EVERY non-terminal return, including an early return triggered by log or phase progress — not just expiry at the bound. A progress wake-up that exited 0 would tell the Bridge the Job had finished mid-run. The set {0, 2, 1} is TOTAL — there is deliberately no fourth code: jobs/02's derived `interrupted` returns 0, because an interrupted Job will never leave that state on its own and a Bridge told 2 would poll a dead Job until the operator gives up; the distinction between completed and interrupted lives in the OUTPUT — `result` names the interrupted status and points at resume — never in the exit code (jobs/02 pins this rule and surface/01's Bridge branches on it). This slice never emits that case itself (it has no crash detection). Two transitions inside one poll interval collapse into one observation; `jobs/<id>.log` is the complete event stream, so nothing is lost.
- `logs <id-or-prefix>`: prints the timestamped log (optionally `--tail N`), plus the spawn log whenever the progress log is empty or absent — keyed on the log being empty, NOT on status `failed`. The pre-claim crash this slice cares most about (worker dies on import, before it can write anything) leaves the record `queued`, so a status-keyed condition would hide the spawn log in exactly the case it was created for.
- One shared resolver in `state.py` backs `status` and `logs` — `resolve_job(arg)`, which jobs/02 and jobs/03 reuse verbatim for their verbs rather than reimplementing: exact id wins over prefix; no match or an ambiguous prefix exits 1 listing candidates, and that includes an explicit id against an empty store. Exit 0 with no output is the answer only to a bare `status` with nothing to list — never to a lookup that named a Job and did not find it.
- `task --profile <name> [--read-only] [--workspace <dir>] [--bash-timeout-s <s>]` with the prompt as argv or on stdin — surface/01's pinned Bridge-facing form plus `--workspace`, which this slice adds for bare-CLI and test callers and the Bridge never sends. It matches `steer`'s argv-or-stdin shape, with the Bridge mandated to use the stdin form so prompts carrying quotes, newlines, or a leading dash survive intact; argv callers separate a prompt starting with `-` using `--`. Reuse jobs/03's pinned semantics verbatim rather than inventing a second dialect: stdin is read ONLY when argv carries no text and stdin is not a TTY (otherwise a bare `task --profile x` at a terminal hangs forever on a read), and an empty prompt is refused before the record is written, the same fail-fast the profile rule exists to give. The flag is spelled `--bash-timeout-s` and populates `request.bashTimeoutSec`. `--timeout-ms` on `status --wait` is capped at the PRD's bounded-window intent (~4 min, the 240 s default); a larger value clamps rather than turning a bounded poll into an unbounded block. Write-capable is the default and `--read-only` the opt-out. The profile is required and resolved through runtime/01's `profiles.py` BEFORE the record is written, so an unknown profile fails fast on stderr instead of becoming a `failed` Job the operator has to go read.
- Explicitly NO SessionEnd/reaper code path anywhere; pruning (jobs/02) never touches running Jobs.

## Acceptance Criteria (from the issue)

- [ ] Dispatch returns a job id in under a second while the detached worker completes the scripted Job afterwards
- [ ] Killing the dispatching process immediately after dispatch does not disturb the worker; state and result survive
- [ ] status shows running→completed with phase and preview; status --wait returns early on completion
- [ ] Two concurrent Jobs complete without corrupting state.json or each other
- [ ] State schema versioned; no code path deletes or kills Jobs at any session boundary

## Tests

- `test_dispatch.py::test_task_returns_id_fast` — `task` against a slow scripted fake provider returns an id within 1 s; the record exists with status queued/running (issue AC bullet 1).
- `test_dispatch.py::test_background_execution` — run `task` inside an intermediate shell so there is a live parent to kill, capture the printed id, SIGKILL that shell's whole process group (never pytest or the in-process fake provider), and assert the worker — in its own session, so outside that group — still transitions the record to completed with the scripted result (AC bullets 1–2).
- `test_dispatch.py::test_spawn_failure_marks_failed` — make the spawn genuinely fail with a real process, not a mocked one (the PRD's testing decisions forbid a mocked process layer): point the worker interpreter at a non-executable path via the documented override so `Popen` raises `OSError` for real. The record ends `failed` with an `errorMessage` and the dispatcher exits non-zero, never leaving a `queued` record with no worker.
- `test_dispatch.py::test_fast_worker_does_not_lose_pid_race` — a worker that claims (and finishes) before the dispatcher's pid write leaves the Job `completed`, NOT `failed`, and the dispatcher exits 0: the pid-write CAS failing is not a dispatch failure.
- `test_dispatch.py::test_persistence_across_parent_death` — state dir contents (record, log, transcript) intact and readable in a fresh process after the dispatcher is long gone (AC bullet 2).
- `test_status.py::test_running_then_completed_preview` — status output shows phase + preview lines while running, then completed (AC bullet 3).
- `test_status.py::test_wait_returns_early` — `status --wait` returns within ~2 poll intervals of the worker finishing, well under the 240 s bound (AC bullet 3).
- `test_status.py::test_wait_wakes_on_log_progress` — a scripted Job that emits progress lines without changing phase wakes `--wait` on the new log lines rather than blocking to the bound, which is what the Bridge's poll-relay depends on (AC bullet 3).
- `test_concurrency.py::test_two_jobs_no_corruption` — two simultaneous dispatches: both complete; `state.json` parses AND contains both ids (a lost index update leaves perfectly valid JSON missing a job, which parse-only assertions miss); both records correct (AC bullet 4).
- `test_state.py::test_index_rebuilt_from_records` — delete/truncate `state.json` with records on disk; the next read rebuilds the index and lists every Job, proving records are the source of truth and a crash between the two writes loses nothing. A Job with a `<id>.result.json` beside its record must rebuild to ONE Job, not two — the strict-filename assertion that a bare `jobs/*.json` scan would fail.
- `test_dispatch.py::test_second_claimant_refuses` — run `task-worker` twice against one `queued` record: exactly one claims it and runs, the other exits without running, and the Job executes once.
- `test_dispatch.py::test_cancel_before_claim_is_not_outrun` — mark a `queued` record terminal, then start its worker: the worker exits without running and never overwrites the terminal status with `running`, which is the invariant jobs/02's cancel path depends on.
- `test_status.py::test_progress_return_exits_two` — a `--wait` that returns early on progress while the Job is still active exits 2, the same as expiry at the bound; only a terminal Job exits 0. The Bridge branches on this code, so a progress wake-up exiting 0 would be read as completion.
- `test_state.py::test_workspace_key_from_subdirectory` — dispatching from a repo subdirectory resolves to the SAME state dir as dispatching from the root, and `workspaceRoot` on the record is the resolved toplevel. The git-toplevel rule exists to stop state fragmenting; nothing else pins it.
- `test_state.py::test_state_root_resolution` — `CLAUDE_PLUGIN_DATA` wins when set; empty or relative values for it or `XDG_STATE_HOME` fall back as if unset.
- `test_state.py::test_permissions` — state dirs 0700 and records/logs/transcript/result 0600, since these files hold prompt text and results.
- `test_state.py::test_pid_start_time_parsed_with_parens_in_comm` — a synthetic `/proc/<pid>/stat` line whose comm contains spaces and parentheses yields the correct field 22. A naive split ships green through every other test in this suite and jobs/02's, then feeds a wrong start-time into a kill decision.
- `test_logs.py::test_spawn_log_surfaced_when_progress_log_empty` — a Job whose worker died before writing any progress line still shows its spawn output through `logs`, whatever its stored status.
- `test_state.py::test_schema_version_present` + `test_reads_tolerate_additive_change` — schemaVersion in every record; a record carrying an unknown extra field and missing an optional one still loads with defaults (AC bullet 5, PRD user story 13).
- `test_state.py::test_no_session_reaper` — this slice's public surface has no session-boundary kill path: `state.py` exposes no delete/reap API keyed on a session, and no CLI verb accepts a session id as a selector (AC bullet 5). The manifest-level half of the invariant — hooks.json registering no SessionEnd entry — is asserted where the manifest actually exists, by surface/02's `test_hooks_registration.py::test_no_session_end`; a grep for "SessionEnd" over a tree with no hooks in it would prove nothing here.
