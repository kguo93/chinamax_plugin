# Plan — Lifecycle verbs

## Solution

Complete the Job lifecycle on the CLI seam: `result` (finished Jobs only), `cancel` (process-tree kill + cancelled status), `resume` (new Job continuing the most recent finished Job's Thread), stale-running crash detection, and pruning — with Codex-derived selection semantics (id-prefix match, latest-for-workspace defaults, ambiguity refusals).

## Implementation Decisions

- Selection and liveness live in ONE place — jobs-01's `state.py`, EXTENDED, never a parallel helper. Every verb here reuses jobs-01's existing shared id resolver verbatim (its shared-resolver decision: exact id, else unique prefix; no match or an ambiguous prefix exits 1 listing candidates), so `result`/`cancel`/`resume` cannot drift from `status`/`logs` — and jobs-03's `steer` resolves "like the other verbs" against this same function. The one addition is `effective_status(record, now)`, which maps a NON-TERMINAL record — `running` **or** `queued` — whose worker is provably gone to `interrupted`, and passes everything else through. `queued` is graded too, not just `running`: jobs-01 writes the child pid onto the record immediately after `Popen` precisely so that a worker dying before it claims the record leaves "a `queued` record whose recorded pid is dead, exactly the shape jobs/02's stale detector grades" (jobs-01's stranded-record decision) — grading only `running` would strand that Job active forever. "Provably gone" = (`os.kill(pid, 0)` raises `ProcessLookupError` — ESRCH ONLY; a `PermissionError`/EPERM means the process exists and must be treated as ALIVE, never dead — **or** the process is a zombie (`/proc/<pid>/stat` state `Z`), which still answers signal 0 and would otherwise read as alive forever — **or** the recorded `pidStartTime` no longer matches, which is the pid-reuse case) AND `updatedAt` is older than the stale grace. `pidStartTime` is jobs-01's field, not this slice's: that slice already captures it beside `pid` and specifies the parse (split after the LAST `)`, since the comm field may itself contain spaces and parentheses — jobs-01's record-schema decision); this slice only CONSUMES it. Degradations are pinned rather than left to the implementer: a record with no usable pid is never signalled and never probed (`os.kill(0, 0)` would hit the caller's own process group); a record missing `pidStartTime` skips the reuse comparison and falls back to the ESRCH test alone (jobs-01's schema decision has readers default missing optional fields); and a `/proc/<pid>/stat` read that fails because the process died mid-check counts as gone, not as an error. `active` = non-terminal and NOT effectively-`interrupted`, so an `interrupted` Job is not active to any verb; no verb re-derives liveness for itself. The "provably gone" inner test is exposed as its own shared predicate beside `effective_status` — jobs/03's relaunch-reclaim arm needs the liveness half WITHOUT the stale grace, and must not re-derive it. "Latest" everywhere means `completedAt` desc, falling back to `updatedAt` for records that have no `completedAt` — which `interrupted` records never do, since their stored status is still `running`/`queued` — then `createdAt` desc, then id desc.
- `result <id?>`: with no id, the latest `completed` Job; an explicit id/prefix resolves across ALL records. Only `completed` carries a payload — jobs-01 maps every `report_result` to `completed` and stores the payload verbatim even when its `outcome` is `failed`/`blocked`, reserving status `failed` for Runtime errors that carry only `errorMessage` (jobs-01's terminal-status decision) — so `result` reports honestly per state rather than inventing an empty payload: `completed` prints the stored report_result payload, and `failed`/`cancelled`/`interrupted` print the status and `errorMessage` instead. Exit codes follow jobs-01's shared convention EXACTLY rather than inventing a verb-local one — 0 = terminal, 2 = still active, 1 = usage or resolution error (jobs-01's exit-code decision, which surface/01 has the Bridge branch on instead of parsing prose). So every terminal Job exits 0 whether or not it had a payload (the difference is in the output, never in the code), an active Job exits 2 pointing to status, and only an unknown/ambiguous id exits 1. `--json` emits the bytes of `jobs/<id>.result.json` as stored — runtime/01's result-fidelity decision writes that file deterministically (`sort_keys=True`; its "verbatim" is SEMANTIC JSON equality, since the SDK reparses `input_json_delta` and provider byte order is unrecoverable) and jobs-01 folds it into the terminal write, so `--json`'s "verbatim" means the stored file's bytes rather than a fresh re-serialization of a parsed value; for a terminal Job with no payload `--json` emits `{"status": …, "errorMessage": …}`. The default rendering walks the payload's seven known fields in schema order (outcome, summary, changed_files, commands_run, tests, failures, concerns), omitting absent optional ones, so the implementer does not invent a format.
- `cancel <id?>`: an explicit id/prefix resolves across ALL records; with no id it resolves the single active Job, refuses when several are active (listing their ids), and exits 1 saying so when none is active. Cancel of an already-terminal Job is a no-op that prints the current status and exits 0. Otherwise it kills the worker's whole process TREE, and the group alone is not the tree: the Runtime's bash tool puts every command in its OWN session (runtime-02's per-command-timeout decision: `start_new_session=True` so a command timeout kills the child's group and not the Runtime's), so a single `killpg` on the worker's group leaves those children running. Cancel therefore snapshots the worker's descendants FIRST — walk ppid links over `/proc/*/stat` from the recorded pid before signalling anything, because orphans reparent to init the instant the worker dies — then SIGTERMs every distinct process group in that set, waits a 10 s grace, RE-scans for descendants that appeared after the snapshot, and SIGKILLs everything still alive. A pid whose `pidStartTime` no longer matches is skipped, never signalled, so a recycled pid or pgid is never the target. The reachable-tree limit is stated rather than papered over: a descendant that fully daemonized before the snapshot has already been reparented away from the worker and cannot be found by ppid traversal — the confined bash tool does not do this, which is why the AC is satisfiable, but cancel claims only what it can verify. It verifies: if anything targeted is still alive after the SIGKILL sweep (EPERM, an unkillable state), cancel reports which pids survived and exits non-zero instead of writing `cancelled` over a Job it did not actually stop. The status write goes through jobs-01's single locked compare-and-swap updater (its record-mutation decision), never an ad-hoc write: re-read under `state.lock` and write `cancelled` + `errorMessage` "Cancelled by user." + `completedAt` + `updatedAt` only if the record is still non-terminal, so a worker that completed during the kill keeps its result instead of having it silently overwritten by a last-writer-wins cancel. Setting `completedAt` is what keeps a cancelled Job orderable by the "latest" key above and freezes its elapsed time in `status`. A not-yet-started Job is marked cancelled directly; that is safe because the worker's own claim is the SAME locked CAS (`queued` → `running`, applied only if still `queued` — jobs-01's worker-claim decision), so the two transitions compete for one lock and the loser exits: the worker finds its record already terminal and exits without running. That mutual exclusion, not ordering luck, is why a cancel cannot be outrun by the worker it was meant to stop.
- `resume [<id-or-prefix>] [prompt]` (the argv surface/01 pins — the Bridge always passes an explicit id): a first argv token beginning `task-` is the target and resolves through the shared resolver (resolution failure exits 1); any other first token starts the prompt, and the target then defaults to the most recent non-active Job with a Thread (`completed`/`failed`/`cancelled`/`interrupted`). The prompt follows task/steer's argv-or-stdin rule (stdin read only when argv carries no prompt and stdin is not a TTY). Refuses while any workspace Job is active ("still running — use status"). The guard, the source resolution, the transcript copy, and the new record's creation all happen inside ONE critical section under jobs-01's `state.lock` flock — the copy included, since creating the record under the lock but copying after it would let a concurrent prune delete the source in between. Two concurrent resumes therefore cannot both observe "nothing active" and both dispatch. The DISPATCHER, not the worker, copies `jobs/<source>.thread.jsonl` into the new Job's own transcript (source left intact); the worker only ever reads its own transcript, so pruning can never delete the source out from under a rehydrating worker. The new Job inherits `profile`, `write`, `workspaceRoot`, and `bashTimeoutSec` from the source's `request` (a resume must not silently change posture or provider), while `sessionId` is the CURRENT session — provenance only, never behavior (ADR 0004). A source whose transcript is absent, empty, or yields no usable turn after normalization is refused with that reason rather than dispatched as an empty Job.
- Resume transcript normalization — one routine, applied to the copy, and it REPAIRS rather than truncates, because dropping turns would break the "full prior history" the AC and `test_resume_continues_thread` assert. Runtime/01's transcript is write-ahead: the outgoing user/tool_result delta is flushed BEFORE the API call and the assistant turn is appended after, and entries are plain non-atomic JSONL appends whose torn trailing line a reader must tolerate (runtime-01's write-ahead decision). Three tail shapes therefore exist and each has a defined repair. (1) A trailing line that does not parse as JSON is dropped — it is a half-written append, not a turn. (2) A trailing assistant turn with unanswered `tool_use` blocks gets a synthetic `tool_result` for each unanswered id, never a dropped turn: a normally-completed Job ALWAYS ends this way, because the loop terminates on the `report_result` tool_use without answering it (runtime-01's loop decision), so dropping it would delete Job A's terminal report from every ordinary resume while also breaking the API's requirement that each `tool_use` be answered. (3) A transcript ending in a user turn — the write-ahead delta of an API call the worker was SIGKILLed during — must NOT be followed by a second user message: the follow-up is merged into that trailing user message as an additional text block, exactly the shape jobs-03's wire-shape decision adopts because "the Profiles target third-party Anthropic-compatible endpoints whose tolerance for consecutive same-role messages is not guaranteed". Otherwise the follow-up is appended as a new user message. When the prompt is omitted it defaults to the literal `Continue the previous task.` Pending steers on the source Job are deliberately NOT carried forward (jobs-03's drain contract pins it: resume's new Job has its own empty queue). This slice also adds the additive `seed_transcript` spec field (optional bool, default false; validated in `spec.py` like `bash_timeout_s`) and the loop's seeding path behind it: task-worker sets it on every spec, and with it set a non-empty transcript is read through this same tolerant repairing reader into the in-memory Messages history and APPENDED to, never truncated by runtime/01's fresh-run default — resume and jobs/03's relaunch recovery both stand on this. Because the normalization above folds the follow-up into a trailing user turn, every seeded resume history ends with an unsent user turn: the loop's first request SENDS that turn (without re-appending it to the transcript) and does NOT append the spec's prompt as a second user message — appending both would deliver the follow-up twice.
- Stale detection: read-side only — nothing ever rewrites a record behind a worker. `status` renders an effectively-`interrupted` Job as `interrupted` (a distinct marker, honest reporting) while the stored status stays `running`, and its Thread stays resumable. The grace window is 60 s. There is no window in which a live worker legitimately lacks a recorded pid — jobs-01's dispatcher writes pid and `pidStartTime` immediately after `Popen` (its detach decision) and the worker's claim is an atomic locked CAS — so the grace is not covering a pid gap; it exists so that a single missed or delayed heartbeat around a crash, a clock skew, or a slow write never flips a Job to `interrupted` prematurely. Because the test is conjunctive (worker provably gone AND heartbeat older than the grace), a live-but-quiet worker is never misreported: jobs-01 refreshes `updatedAt` at least every 30 s from a daemon thread even with nothing changing — expressly because the loop blocks for minutes inside one API call or bash command and so cannot drive its own heartbeat — and pins the pairing, "the interval jobs/02's stale detector explicitly grades against, its 60 s grace being twice this; these two numbers move together or stale detection breaks" (jobs-01's record-freshness decision). `interrupted` is a derived observation, not a stored terminal status, and callers read it as "will not progress further", not as a result. For `status --wait` that means an effectively-interrupted Job returns IMMEDIATELY with exit 0 rather than spinning to the 240 s bound: 0 is jobs-01's code for "the Job is in a terminal state", and an interrupted Job will never leave this one on its own, so a poll-relay that kept waiting would hang for the life of the Bridge. The Bridge then calls `result`, which names the interrupted status and points to resume — the distinction lives in the output, not in a third exit code. surface/02's SessionStart digest already renders interrupted Jobs as their own category alongside running and completed ones.
- Pruning: runs under jobs-01's `state.lock` flock, and only on dispatch and on terminal transitions — not on every throttled progress update or steer write, which would scan-and-delete constantly and widen the window where a concurrent `logs`/`result` read hits a half-deleted Job. Keeps the newest 50 finished Jobs, where finished = `completed|failed|cancelled`. It deletes EVERY file in jobs-01's authoritative per-Job layout list (its state-layout decision), which is SIX artifacts, not five: `.json`, `.log`, `.spawn.log`, `.thread.jsonl`, **`.result.json`**, and the `.steer/` directory RECURSIVELY. Both of the last two are traps: jobs-01's layout bullet requires any addition there to be mirrored here or prune leaves orphans, and jobs-03's consumed/ decision nests a subdirectory inside the steer queue that a flat unlink loop leaves behind. Deletion order is record-`.json` FIRST, then the sidecars: the record is what makes a Job resolvable, so dropping it first means a concurrent `logs`/`result` either resolved the Job before the prune began or cannot see it at all, instead of resolving it and then reading a half-deleted set. `state.json` is updated in the same locked transaction, record-then-index per jobs-01's store-invariants decision, so no pruned id stays resolvable through the cache. Missing files are tolerated so prune is idempotent after a crash, and symlinks are never followed. Active and `interrupted` Jobs are never pruned and never counted toward the 50 — pruning a Job whose Thread is still resumable would destroy exactly the crash-recovery the fourth acceptance criterion demands, so an interrupted record persists until the operator resumes or the Job is explicitly cancelled.

## Acceptance Criteria (from the issue)

- [ ] result returns the payload for finished Jobs; refuses active Jobs with guidance
- [ ] cancel kills the whole tree (verified dead), sets cancelled + reason; ambiguous cancel refuses with the active list
- [ ] resume creates a new Job continuing the prior transcript (fake provider sees full history); refuses while active
- [ ] SIGKILLed worker detected as interrupted; Thread resumable afterwards
- [ ] Pruning removes oldest finished beyond ~50 (with files) and never a running Job

## Tests

- `test_result.py::test_result_finished` / `test_result_refuses_active` — exact stored payload returned (and `--json` emits it verbatim); active Job → exit 2 + guidance to status (issue AC bullet 1).
- `test_cancel.py::test_cancel_kills_tree` — worker running a scripted bash child that is spawned in its OWN session, mirroring runtime-02's `start_new_session=True` bash tool: after cancel, worker AND child pids are dead. This own-session child is the point of the test — a child sharing the worker's group would pass under a single `killpg` and let the real defect through. Record ends cancelled with reason (AC bullet 2).
- `test_cancel.py::test_ambiguous_cancel_refuses` — two active Jobs, no id: refusal lists both ids (AC bullet 2).
- `test_cancel.py::test_cancel_does_not_clobber_completed_result` — let the Job reach `completed` before cancel writes its status: the record keeps `completed` and its result payload, and cancel reports the terminal status instead of overwriting it (guards the compare-and-swap).
- `test_resume.py::test_resume_continues_thread` — finish Job A (scripted); resume with a follow-up: the fake provider's first request of Job B contains A's full message history — INCLUDING A's terminal `report_result` assistant turn, answered by the synthetic tool_result rather than dropped — then the follow-up as the newest user message; A's transcript is still intact on disk (AC bullet 3). Also asserts B's record inherited A's profile and write posture.
- `test_resume.py::test_resume_refuses_while_active` (AC bullet 3).
- `test_stale.py::test_sigkilled_worker_reported_interrupted` — SIGKILL the worker, then age `updatedAt` past the 60 s grace rather than sleeping it out: status shows interrupted, not running/completed, and `status --wait` returns immediately with exit 0 instead of blocking to the bound; the Job counts as non-active, so a subsequent resume of its Thread succeeds even though the stored status is still `running` (AC bullet 4).
- `test_stale.py::test_queued_job_with_dead_pid_is_interrupted` — a `queued` record whose recorded pid is dead and whose `updatedAt` is aged past the grace grades as interrupted, not active: this is the worker-died-before-claiming shape jobs-01's stranded-record decision hands to this detector, and grading only `running` would strand the Job active forever.
- `test_stale.py::test_resume_normalizes_torn_transcript` — parametrized over the three tail shapes: a truncated final JSONL line (dropped), an unanswered non-terminal `tool_use` turn (answered with the synthetic tool_result, turn preserved), and a transcript ending in a user turn (follow-up merged into it, so the request carries NO two consecutive user messages). Each yields a message sequence the fake provider accepts (the SIGKILL path of AC bullet 4).
- `test_prune.py::test_prunes_beyond_cap_files_removed` + `test_prune.py::test_never_prunes_running` — seed 55 finished records (+1 running, +1 stale/interrupted): 50 finished remain; every pruned Job's `.json`, `.log`, `.spawn.log`, `.thread.jsonl`, `.result.json`, and its whole `.steer/` tree including `consumed/` are gone — the assertion enumerates all six artifacts of jobs-01's layout list so a future addition to that list fails here loudly rather than leaking orphans; pruned ids no longer resolve through `state.json`; the running and interrupted records are untouched and uncounted (AC bullet 5).
