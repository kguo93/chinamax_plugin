# Plan — Runtime walking skeleton

## Solution

Build the thinnest complete Runtime path: `python -m chinamax exec <spec.json>` reads a job spec (workspace, profile, prompt, transcript/result paths, write flag, job id), resolves the Profile, builds an `anthropic` SDK client for its base_url/model, and runs a streaming Messages tool-use loop with exactly two tools — `bash` (cwd-pinned) and `report_result` — appending every turn to the Job's Thread transcript (JSONL) and terminating when the model calls `report_result`, captured verbatim. The hermetic fake provider server is built alongside as the permanent test bed.

## Implementation Decisions

- Package: `src/chinamax/` (installed `pip install -e .` into conda env `chinamax`, python 3.12; runtime dep: `anthropic>=0.37,<1` — the floor establishes that the `auth_token` / `messages.stream` / `max_tokens` API this plan relies on is present (verified against the locally installed 0.37.1), and the ceiling keeps a future major release from silently changing a protocol-critical dependency; test extra `[test]` = `pytest`, declared as `[project.optional-dependencies]` so the verification command's `.[test]` resolves). `pyproject.toml` needs three stanzas the implementer would otherwise have to guess: `[build-system] requires = ["setuptools>=61"]`, `[tool.setuptools.packages.find] where = ["src"]` for the src layout, and `[tool.setuptools.package-data] chinamax = ["data/*.json"]` — a wheel omits non-`.py` files by default, and the editable install used in verification would hide that until the plugin ships.
- Modules: `profiles.py` (resolution), `provider.py` (client construction), `loop.py` (the agent loop), `tools/` (registry; this slice: bash, report_result), `transcript.py` (JSONL Thread), `spec.py` (job-spec parse/validate), `__main__.py` (CLI seam — this slice ships only `exec`; later slices add subcommands to this same entrypoint).
- Job spec (`spec.py`) — the frozen public contract slice 02 and the jobs scope extend, so it is pinned here rather than invented: a JSON object with required `workspace` (absolute path to an existing directory), `profile` (name), `prompt` (non-empty string), `transcript_path` (absolute path for the Thread JSONL; parent directory created if absent) and `result_path` (absolute path the verbatim `report_result` payload is written to as JSON); optional `write` (bool, default true) and `job_id` (string, provenance only — no behavior keys off it). Missing required keys, wrong types, and unknown keys fail validation before any provider call, exiting non-zero naming the offending field. The two paths are caller-supplied precisely because the state dir belongs to the jobs scope: the jobs-01 plan's state-layout decision passes its per-Job `jobs/<id>.thread.jsonl`, while slice-01 tests pass tmp paths. Validation also rejects a spec where `transcript_path` and `result_path` name the same file, which would otherwise interleave a JSONL stream into the result document. Both are opened fresh per run: an existing `transcript_path` is truncated rather than appended to — the fresh-run default, so re-running a spec cannot graft a new conversation onto stale history; the jobs scope's task-worker instead sets the additive `seed_transcript` spec field (jobs/02 owns it) to seed-and-append from an existing transcript, which is what makes worker relaunch and resume able to continue a Thread — and `result_path` is written atomically (tmp + rename) so a crash mid-write never leaves torn JSON for the jobs scope to parse.
- Sibling-plan references throughout this plan are by DECISION, not by line number: the sibling plans are edited concurrently and line citations go stale (two did between this plan's drafting and its review). Cite the neighbouring decision by name and let the reader find it.
- Profiles: `src/chinamax/data/profiles.json` shipped with exactly the 5 pro rows, each `{name, base_url, model, api_key_env}` plus optional `max_tokens` — deepseek → `https://api.deepseek.com/anthropic` / `deepseek-v4-pro[1m]` / `DEEPSEEK_API_KEY`; mimo → `https://api.xiaomimimo.com/anthropic` / `mimo-v2.5-pro[1m]` / `MIMO_API_KEY`; glm → `https://api.z.ai/api/anthropic` / `glm-5.2[1m]` / `GLM_API_KEY`; minimax → `https://api.minimax.io/anthropic` / `MiniMax-M3[1m]` / `MINIMAX_API_KEY`; kimi → `https://api.moonshot.ai/anthropic` / `kimi-k3` / `KIMI_API_KEY`. Base URLs and model strings are verbatim from implement-handoff (SKILL.md lines 43-50); the env-var NAMES are verbatim only for deepseek/mimo/kimi — implement-handoff carries glm's and minimax's tokens as inline literals, and CLAUDE.md line 21 records that those two were appended to model-keys.env as `GLM_API_KEY`/`MINIMAX_API_KEY`. `max_tokens` defaults to 32000; that figure is a plan-level choice with no ADR or PRD backing, which is exactly what the per-row override is for — if a provider rejects it, fix the row, not the code.
- Profile overlay and keys: merge `~/.claude/chinamax-profiles.json` when present, FIELD-BY-FIELD within the row matched by `name` (an overlay row supplying only `model` keeps the shipped `base_url`/`api_key_env`); an overlay row whose name is not shipped adds a profile, and must then carry the full `{base_url, model, api_key_env}` set. Overlay validation is as strict as the job spec's: malformed JSON, a duplicate name, an unknown field, or a non-positive/non-integer `max_tokens` exits non-zero naming the file and the offending row rather than silently falling back to the shipped set. Keys: parse `~/.claude/model-keys.env` — blank lines and `#` comments ignored, `KEY=VALUE` lines with the value unquoted by shell rules (`shlex`), NOT a bare `split("=", 1)`. This is load-bearing: the real file single-quotes three of its five values while implement-handoff consumes it by bash-sourcing (SKILL.md line 223), so a naive split hands the provider a token wrapped in literal `'` characters and every deepseek/mimo/kimi dispatch fails auth while the hermetic suite stays green. All `~/.claude/...` paths resolve through `Path.home()`, never a hardcoded `/home/...` — that is what lets the suite run keylessly under a temp `HOME`. A profile whose `api_key_env` is absent or empty in that file exits non-zero naming the missing variable. No default Profile: spec without a profile name, or naming an unknown one, exits non-zero with the configured profile list on stderr.
- Client: `anthropic.Anthropic(base_url=row.base_url, auth_token=key, max_retries=0)` — bearer auth matching implement-handoff's ANTHROPIC_AUTH_TOKEN usage, NOT `api_key`/x-api-key. Passing `auth_token` alone is NOT sufficient to guarantee bearer auth: the SDK falls back to `os.environ["ANTHROPIC_API_KEY"]` whenever `api_key` is None (`anthropic/_client.py` — "if api_key is None: api_key = os.environ.get(...)"), and `auth_headers` returns `_api_key_auth` BEFORE `_bearer_auth`, so an ambient `ANTHROPIC_API_KEY` silently sends `X-Api-Key` and no `Authorization` header — against the real providers, not just in tests. The shared exec entry (the same validated entry jobs/01's task-worker later calls in-process — the sanitization must live there, not in the `exec` verb handler alone) therefore pops `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, and `ANTHROPIC_BASE_URL` from `os.environ` before constructing any client, so the Profile is the only source of endpoint and credential. This is a real-machine defect, not a test artifact: the operator's shell is a plausible carrier, and the keyless-HOME test guarantee does not cover process env vars. `max_retries=0` is deliberate: the SDK otherwise retries twice by default (`anthropic/_constants.py` line 10, `DEFAULT_MAX_RETRIES = 2`), which would silently nest underneath slice 03's ~6-attempt ladder and make the Runtime's retry accounting wrong. Slice 03 owns retries outright. The SDK's 600 s default request timeout stands for now; slice 03 replaces it with the streaming inactivity timeout. No Claude-Code-only extras (effort env vars do not translate to the wire; omit).
- Loop: `client.messages.stream(...)` per turn; system prompt states the workspace, write posture, and the report_result completion contract. EVERY `tool_use` block in an assistant turn is executed in arrival order and answered by a `tool_result` carrying the matching `tool_use_id`; a tool name outside the two-tool registry returns an error `tool_result` rather than raising, so no model-chosen name can kill the Job. The loop repeats until a `report_result` tool_use arrives — its input is stored verbatim as the Job result ({outcome: completed|blocked|failed, summary, changed_files, commands_run, tests, failures, concerns}); when `report_result` shares a turn with other tool_use blocks, those are executed, answered, and their tool_results APPENDED TO THE TRANSCRIPT before the loop terminates — even though no further request is sent — so the Thread never ends with a tool_use the durable record leaves unanswered. The one deliberate exception is the terminal `report_result` block itself, which is recorded unanswered because it IS the terminus; a resuming reader answers it with a synthetic `tool_result` rather than dropping the turn or replaying it unanswered (jobs/02's normalization pins that repair — dropping would delete the terminal report from every resume). If a single turn somehow carries two `report_result` blocks, the first in arrival order wins and the rest are ignored. Each advertised tool carries an `input_schema` (the SDK requires one): bash takes `{command: string}`, and `report_result` declares all seven fields with `outcome` (enum) and `summary` (string) required, `changed_files`/`commands_run`/`tests`/`failures`/`concerns` optional arrays of strings. A tool_use whose input does not satisfy its schema returns an error tool_result, never an exception. The bash tool_result carries the exit code and the captured stdout/stderr so both are inspectable.
- Result fidelity: the payload is stored with no normalization, no field synthesis, and no audit (ADR 0007). "Verbatim" here means SEMANTIC JSON equality, not byte equality — the SDK accumulates `input_json_delta` chunks and parses them into `content.input`, so re-serializing cannot preserve the provider's original whitespace or key order. The result file is written with `json.dump(..., sort_keys=True)` and compared by parsed equality, which makes the guarantee deterministic by construction instead of by accident of dict ordering.
- Termination totality: an assistant turn carrying NO tool_use blocks yields no tool_results, so re-sending would repeat the same request indefinitely. Such a turn is answered with a user message restating the report_result contract, which advances the conversation. The condition keys on the ABSENCE OF TOOL_USE BLOCKS, never on `stop_reason == "end_turn"`: `max_tokens` and `stop_sequence` produce the same tool-less turn, and an implementation keyed on `end_turn` would loop unboundedly on both. This introduces no wall-clock and no turn cap — ADR 0002 still forbids both; it only makes the loop total over stop reasons, keeping report_result the sole terminal path (PRD line 39).
- API errors in this slice: with `max_retries=0` and the retry ladder deferred to slice 03, a 429/5xx/connection error or a mid-stream `error` event raises out of the loop. That is the intended slice-01 behavior — do NOT add ad-hoc retry here, it would collide with slice 03's ladder. The Runtime catches it at the CLI seam, writes the terminal error where the jobs scope can classify it, and exits 1.
- Transcript is write-ahead (PRD line 43 — "written before/after every API call"; the jobs-03 steer-drain decision explicitly relies on runtime-01 flushing before the call): the outgoing user/tool_result delta is appended and flushed BEFORE the API call, and the assembled assistant turn is appended after the stream completes. Appending both after the turn would lose the outgoing state to a mid-stream crash and break the steer slice's exactly-once drain. A crash mid-stream therefore leaves a legitimate intermediate state — an outgoing delta with no answering assistant turn — which readers must accept rather than treat as corruption. Entries are plain JSONL appends and are not atomic, so a reader also tolerates a torn trailing line (the jobs-02 resume decision depends on this).
- Transcript record schema, versioned now because five downstream slices read it: every line is an object with `v` (schema version, `1`), `ts` (ISO-8601), and `kind`. `kind: "message"` records carry `role` and `content` and ARE the replayable conversation; every other kind is metadata that a replay skips. This slice emits only `message`; the discriminator exists so the runtime-03 retry events (and any future non-replayable metadata) can be added without a format break or a guess about which lines rebuild the API history. The jobs-03 steer entry is NOT such a metadata kind: it stays a replayable `message` record — its steer id and enqueue timestamp ride as additive metadata FIELDS beside `v`/`ts`/`kind` on that record — because the steer's text is part of the user turn the provider actually saw, and a replay that skipped it would reconstruct a different conversation than the wire carried.
- bash tool (this slice): `subprocess` running `bash -c <command>` — the scripted `echo hello > out.txt` needs shell redirection — with cwd=workspace and the exit code in the tool_result. stdout and stderr are each drained into their own bounded ~50 KB tail buffer as output arrives, rather than accumulated whole and truncated afterwards: with no command timeout until slice 02, a runaway command must not be able to exhaust Runtime memory, and the slice-02 tool registry reuses this same truncation mechanism. The two pipes MUST be drained concurrently (reader threads or `selectors`) — a sequential read of one pipe deadlocks once the other fills its buffer, which is exactly the runaway case these buffers exist for. Output is decoded with `errors="replace"` so binary output cannot raise. Denylist/timeout/confinement hardening arrives in slice 02 — but cwd-pinning exists now.
- The spec's `write` flag is ADVISORY in this slice: it shapes only the system prompt's write posture. Read-only ENFORCEMENT — write-class tools omitted from the schema and dispatch, write-shaped bash refused — is the slice-02 read-only-mode decision's, so a `write: false` Job here can still write through bash. Stated so the implementer neither builds enforcement early nor mistakes the flag for a guarantee.
- Fake provider: `tests/fake_provider.py` — stdlib `http.server`/`ThreadingHTTPServer` on an ephemeral port serving `POST /v1/messages` with SSE streaming events from a per-test scripted turn list; records every request's BODY AND HEADERS for assertions (the bearer-auth test reads headers); supports scripted faults (used from slice 03 on). The wire grammar is spelled out here because none of the cited context files carries it and the banner above forbids inferring, and three details are SDK-enforced rather than cosmetic — get them wrong and the stream yields zero events or fails validation:
  - Each SSE frame must carry an `event:` line, not just `data:`. The SDK dispatches on the SSE event NAME (`anthropic/_streaming.py` switches on `sse.event`) and injects `type` from it; a frame with only `data:` is silently dropped.
  - `message_start` must carry a COMPLETE `Message` — `id`, `type`, `role`, `model`, `content`, `usage` — not merely `message.usage`. Every event is validated by pydantic.
  - `message_delta` requires BOTH `delta` (carrying `stop_reason`) and a `usage` object; `usage` is non-optional on `RawMessageDeltaEvent`.
  Between those come the per-block events `content_block_start` / `content_block_delta` / `content_block_stop`, each with its `index` — `text_delta` for text blocks and `input_json_delta` chunks carrying the partial JSON of a `tool_use` block's `input` — and the stream closes with `message_stop`. Each event is flushed as written so the SDK sees a real stream. Build these through one fixture helper rather than hand-rolling frames per test.
- Fake-provider fixture lifecycle (it is the permanent test bed for every later slice, so its contract is pinned now): function-scoped — each test starts its own server, reads back the bound port, and tears it down deterministically with `shutdown()` THEN `server_close()` then a join of the serving thread. `shutdown()` alone only stops the `serve_forever` loop; `server_close()` is what closes the listening socket and joins outstanding handler threads, so omitting it leaks a socket per test. Both the request log and the scripted-turn cursor are mutated under a lock, since `ThreadingHTTPServer` serves each connection on its own thread. A request arriving after the script is exhausted returns a distinctive 500 with a marker body rather than hanging: the loop has no turn cap by design (ADR 0002) and the suite sets no global timeout, so without this a termination bug spins forever instead of failing in one turn.
- Loop tests bind their Profile to the fake by writing a per-test overlay `chinamax-profiles.json` into the temp `HOME` whose row points `base_url` at `http://127.0.0.1:<port>` — the same override path production uses. There is deliberately no env-var backdoor for the endpoint; the overlay IS the seam, which keeps the tests exercising the real resolution path.

## Tests (all in `tests/`, expected values from the issue/PRD, never from the implementation)

- `test_fake_provider.py::test_scripted_stream_roundtrip` — a scripted text-only turn is served as valid SSE and consumed by a raw SDK client (verifies issue AC bullet 1).
- `test_walking_skeleton.py::test_bash_then_report_result` — script: turn 1 = tool_use bash `echo hello > out.txt && cat out.txt` (the `&& cat` matters: a bare redirect leaves stdout empty, which would make the next test vacuous); turn 2 = report_result with ALL seven fields populated. Assert `out.txt` exists with `hello`, exit code 0, and that the stored result at `result_path` — parsed, then compared as JSON — equals the scripted payload across all seven fields. Compare parsed values, not file bytes: the SDK reparses `input_json_delta` into a dict, so a byte comparison would assert on serialization formatting rather than on payload fidelity (AC bullet 2).
- `test_walking_skeleton.py::test_tool_result_returned_to_provider` — the recorded second request contains a tool_result block whose `tool_use_id` matches turn 1's tool_use and whose content carries the command's actual stdout (`hello`) and exit code (AC bullet 2).
- `test_walking_skeleton.py::test_tool_less_turn_is_nudged` — parametrized over `stop_reason` in {`end_turn`, `max_tokens`, `stop_sequence`}: turn 1 = text only with that stop reason, turn 2 = report_result. Assert the recorded second request appends a user message (not a resend of the first) and the run terminates. Parametrizing is the point — an implementation keyed on `end_turn` passes one case and loops forever on the other two.
- `test_walking_skeleton.py::test_bearer_auth_and_advertised_tools` — with `ANTHROPIC_API_KEY` DELIBERATELY SET in the test process, the recorded first request still carries `Authorization: Bearer <profile key>` and no `x-api-key` header, and advertises exactly the two tools `bash` and `report_result`. Seeding the variable is the whole test: without it the assertion passes even on an implementation that never sanitizes the environment, and the defect only appears on the operator's machine.
- `test_walking_skeleton.py::test_report_result_sharing_a_turn` — script one turn carrying both a bash tool_use and a report_result. Assert the bash side effect happened, its tool_result was persisted to the transcript, and the run terminated without a further request (pins the termination-with-siblings rule).
- `test_transcript.py::test_transcript_reconstructs_history` — after the run, replaying the JSONL at `transcript_path` yields the exact message sequence the fake provider received in its final request plus the final assistant turn (AC bullet 3).
- `test_transcript.py::test_outgoing_delta_written_before_call` — the fake provider, at the moment it receives turn 2's request, RECORDS a snapshot of the transcript file; the test then asserts in the MAIN thread that the snapshot already contained turn 1's tool_result delta. The observation must be recorded and asserted this way, never `assert`ed inside the handler: `http.server` swallows handler exceptions to stderr, so an in-handler assertion is silently vacuous and the test would pass against the very implementation it exists to catch. This is the write-ahead ordering the jobs-03 steer drain depends on (AC bullet 3).
- `test_spec.py::test_spec_validation` — parametrized over a missing required field, a wrong-typed field, an unknown key, and a non-existent workspace: each exits non-zero naming the offending field, with no request reaching the fake provider.
- `test_profiles.py::test_five_shipped_rows` — resolution with no override lists exactly deepseek, mimo, glm, minimax, kimi with the implement-handoff base_urls/models (AC bullet 4).
- `test_profiles.py::test_override_merge` — an override file changing deepseek's model wins for deepseek and leaves the other four untouched (AC bullet 4).
- `test_profiles.py::test_keys_resolved_from_env_file` — a temp model-keys.env supplies the key; resolution returns it for the profile's api_key_env. The fixture reproduces the real file's mixed quoting — single-quoted values for some rows, bare values for others — and extends it with a `#` comment and a blank line, which the real file happens not to contain but the parser must handle. The quoting is the part that must mirror reality: a fixture written entirely unquoted would leave the quote-stripping requirement above asserted nowhere (AC bullet 4).
- `test_profiles.py::test_missing_profile_fails_fast` / `test_unknown_profile_fails_fast` — exec exits non-zero, stderr names the valid profiles (AC bullet 4).
- `test_profiles.py::test_missing_key_fails_fast` — a known profile whose `api_key_env` is absent from model-keys.env exits non-zero naming the missing variable; the only profile-resolution error branch otherwise uncovered (AC bullet 4).
- `test_profiles.py::test_override_adds_and_partially_merges_row` — an overlay row supplying only `model` for deepseek keeps the shipped `base_url`/`api_key_env`, and an overlay row with a new name is added to the set (pins field-level merge against full-row replace) (AC bullet 4).
- Keyless guarantee: an AUTOUSE fixture points `HOME` at a temp dir containing a synthetic model-keys.env and `monkeypatch.delenv`s `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL`, so every test — including ones added by later slices — is keyless and endpoint-clean by default rather than by remembering to opt in. This only holds because every `~/.claude/...` path resolves through `Path.home()`. The one deliberate exception is `test_bearer_auth_and_advertised_tools`, which re-sets `ANTHROPIC_API_KEY` on purpose (AC bullet 5).
