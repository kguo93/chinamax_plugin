# Plan — Steer queue

## Solution

Durable mid-run steering end-to-end: `steer <job> <message>` appends an ordered file to the Job's steer queue; the Runtime drains the queue at each loop-iteration boundary, injecting each steer as a user message into the Thread (transcript + log recorded) before the next API call.

## Implementation Decisions

- Modules — extend, never duplicate: queue read/write helpers join `state.py` beside its existing atomic tmp+rename writes and advisory lock (jobs-01); the `steer` verb joins the `__main__.py` CLI seam; the drain hook goes at the top of `loop.py`'s iteration; the steer entry joins `transcript.py` (runtime-01).
- Queue = `jobs/<id>.steer/` (already created empty at dispatch, jobs-01); each steer a file named `<epoch-ms>-<seq>-<6 rand>.md`, reusing jobs-01's own id shape. Every component earns its place: `epoch-ms` is fixed-width and gives write order across processes; `seq` is a per-process counter zero-padded to `%04d` and orders a same-process burst inside one millisecond (unpadded, `-10` would sort before `-2`); the random suffix makes the name unique outright, so two `steer` processes landing in the same millisecond cannot collide. Uniqueness by construction is what lets the write stay a plain atomic tmp+rename through `state.py`'s existing helper — do NOT reach for an exclusive-create dance: `os.link` would strand the tmp inode, and `open(final, O_CREAT|O_EXCL)` written in place would expose a half-written file to a concurrent drain, breaking this bullet's own no-partial-read guarantee. A name derived by re-listing the directory would be worse still: it can reuse an id whose same-millisecond predecessor already moved to `consumed/`, and the drain's dedupe would then silently swallow the NEW steer while the verb reported success. Tmp files are named `.tmp-<rand>` with no `.md` suffix, so the drain's glob skips them without needing a special case.
- `steer <job> <message>`: `<job>` resolves by id or id-prefix like the other verbs, erroring clearly when unknown or ambiguous. Accepts `queued` and effectively-`running` Jobs; refuses the three terminal states (`completed|failed|cancelled`) with a message pointing to resume. Message precedence is argv first; stdin is read only when argv carries no message AND stdin is not a TTY, so a bare `steer <job>` at a terminal errors immediately instead of hanging on a read that will never end. Empty or whitespace-only input exits non-zero and writes no file, and a message beyond a fixed cap (~256 KB) is refused the same way rather than being queued into a certain provider 400. Enqueue and the worker's terminal transition are not synchronized, so after the queue file lands the verb re-reads the record: if the Job went terminal in the meantime the operator is told the steer was NOT delivered and pointed to resume, rather than being left to believe a never-drained file was accepted. This narrows the window but cannot close it — see the terminal sweep below, which is what makes the remaining case honest.
- Status handling leans entirely on jobs-02's `effective_status` in `state.py`; this verb never re-derives liveness for itself (jobs-02 pins that rule for every verb). An effectively-`interrupted` Job is therefore not `running`, and steering one is refused rather than accepted: the only thing that would ever drain that queue is an internal `task-worker` relaunch on the same Job, because `resume` deliberately does NOT carry pending steers forward (jobs-02) — it builds a new Job with its own empty queue. Accepting a steer no user-facing path can deliver is exactly the false success the re-read above exists to prevent.
- Drain — exactly one process drains a Job's queue (one worker per Job, PRD), so no drain lock and no transcript-append lock are needed. That invariant is upheld by the claim CAS rather than by a drain lock: a `task-worker` launched against a Job whose worker is ALIVE fails jobs-01's claim (with this plan's reclaim arm admitting only a provably-dead worker's Job) and exits without running, and jobs-02's resume guard and compare-and-swap cancel keep a second worker off a live Job from the verb side — so a stray relaunch cannot double-drain or interleave JSONL appends. At the top of every loop iteration, including the first (so a steer written before the worker starts is drained before the first API call), the Runtime lists the queue — `*.md` files only, skipping the `consumed/` subdirectory — and reads them in filename order. For each steer it appends a transcript entry carrying the steer id (its filename), the enqueue timestamp, and the text; only once that batch is flushed does it rename the file into `jobs/<id>.steer/consumed/` (`makedirs(exist_ok=True)` first, since jobs-01 creates only the queue dir itself; the rename crosses directories but is atomic because it stays on one filesystem). The order is load-bearing: commit to the transcript first, acknowledge second. Renaming first loses the steer outright to a crash in the gap — it is then in neither the queue nor the transcript.
- Transcript record shape: the steer's text participates in replay as part of the user turn, while the steer id and enqueue timestamp ride as metadata on that same entry — audit fields, not a content block. Replay must reconstruct the exact Messages content the provider saw, so the metadata has to be recoverable without becoming a content block of its own.
- Exactly-once across restarts: transcript-then-rename is at-least-once on its own, since a crash after the flush but before the rename leaves the file queued. The drain closes that duplicate window by skipping any queue file whose steer id already appears in the transcript, renaming it straight into `consumed/` without re-injecting it. That dedupe is only sound because of the seeding contract jobs-02 owns (its `seed_transcript` spec field, which task-worker sets on every spec): a worker starting on a Job whose transcript is non-empty seeds its in-memory Messages history from that transcript before its first iteration, using the same tolerant REPAIRING reader jobs-02 specifies — a trailing line that does not parse as JSON is dropped, while a trailing assistant turn whose `tool_use` blocks have no matching `tool_result` is KEPT and answered with a synthetic `tool_result` per unanswered id, never dropped (jobs-02's repair rule). Without that seeding the dedupe would be actively harmful — the steer id sits in the transcript, the drain therefore skips it, and the provider never sees it at all: zero deliveries rather than one. The tolerant reader matters here specifically because this scan runs in exactly the crash-recovery path where a torn final line is expected; a strict parser would fail the drain in the one situation the dedupe exists to serve. The scan happens once at worker startup into an in-memory set of consumed steer ids, which later iterations update as they drain, so a long Job never re-parses a growing JSONL at every loop boundary.
- Scope of the guarantee: exactly-once here means one logical steer entry in the reconstructed Thread history. It is not a claim about provider-side processing — a worker that dies after the provider accepted a request but before the response was recorded cannot be made exactly-once by any local protocol, and these endpoints offer no idempotency key. The crash model is process death (SIGKILL), which is what the tests inject and what the sibling slices assume; surviving machine failure would additionally require fsync of the transcript and of the queue directory after each rename, and is deliberately out of scope.
- Wire shape: a drained steer rides in the outgoing user turn as an additional text block on the user message already carrying that turn's `tool_result` blocks, not as a second consecutive `user` message — the Profiles target third-party Anthropic-compatible endpoints whose tolerance for consecutive same-role messages is not guaranteed, and a 400 here would be a self-inflicted turn failure. On the very first iteration the outgoing user message is the original prompt, and the steer is appended to it as an additional text block exactly the same way — it never replaces the prompt. Only when there is no outgoing user message at all does the steer become one on its own. Each steer's text carries the exact marker prefix `[steer] ` (fixed, not illustrative — the tests assert on it).
- Log: one timestamped line per drained steer carrying the steer id and a truncated single-line excerpt; the full text lives in the transcript and the `consumed/` file. Building that excerpt strips control characters generally — carriage returns, tabs, ANSI escapes, and Unicode line separators, not newlines alone — since any of them can otherwise forge or obscure a log line.
- Terminal sweep: when the worker reaches its terminal transition it lists the queue one last time and logs the ids of any steers still sitting there as undelivered. This changes no delivery semantics; it just means a steer that lost the accept-versus-terminate race leaves an auditable trace instead of vanishing silently. Closing that race properly would need a lock spanning the CLI's enqueue and the detached worker's completion path, which is far more machinery than a rare race warrants.
- `consumed/` nests a directory inside `jobs/<id>.steer/`, so jobs-02's pruning must delete that queue recursively; a flat unlink loop over the steer files leaves the directory behind and fails. (jobs-02 already carries this requirement.)
- Relaunch claim — the one edit this slice makes to jobs-01's task-worker: `test_survives_restart_between_write_and_drain` relaunches `task-worker` on the SAME Job, which jobs-01's `queued`-only claim CAS would refuse (the crashed worker's record still says `running`). This slice adds a reclaim arm through the same locked CAS: a NON-terminal record whose recorded worker is PROVABLY GONE — jobs-02's exposed shared predicate (ESRCH-only, zombie state, or `pidStartTime` mismatch), deliberately WITHOUT the 60 s stale grace, since an explicit relaunch verifies liveness directly rather than guarding against a delayed heartbeat — is re-claimed by writing the new worker's pid and `pidStartTime`; a live claimant still causes exit-without-running. No verb path calls this; only `task-worker` startup does.
- Test seams this slice has to build — none exist yet, and without them several of the tests below would be timing-dependent and flaky: a gate in the fake provider that blocks before serving a scripted turn until the test releases it (runtime-01 ships scripting, recording, and faults, but no gating); an abort point in the drain that kills the worker in the window between the transcript flush and the rename; and a clock override the `steer` CLI subprocess honors so two writes can be forced into a single epoch-ms. All three are test-only hooks.

## Acceptance Criteria (from the issue)

- [ ] A steer written between scripted turns appears as a user message in the very next request the fake provider receives
- [ ] Multiple steers inject in write order, exactly once each, surviving a simulated worker restart between write and drain
- [ ] Steers visible in the Thread transcript and progress log with timestamps
- [ ] Steering a finished Job refuses and points to resume; unknown Job errors clearly

## Tracking

- [ ] steer verb + job resolution (incl. `effective_status`) + refusals
- [ ] queue write (unique `<ms>-<seq>-<rand>` name, atomic tmp+rename) / drain / consumed mechanics
- [ ] transcript-then-rename ordering + startup transcript seeding (jobs-02's `seed_transcript`) + steer-id dedupe set
- [ ] relaunch reclaim arm in the claim CAS (jobs-02's provably-gone predicate, no grace)

## Tests

- `test_steer.py::test_steer_lands_next_turn` — hold the fake provider at its turn gate, write a steer, release: the next recorded request carries the steer, marker included, as a text block in its user turn — and that turn is a single user message, not two consecutive ones (issue AC bullet 1).
- `test_steer.py::test_order_and_exactly_once` — three steers written in order; provider records them once each, in order; consumed/ holds all three files (AC bullet 2).
- `test_steer.py::test_survives_restart_between_write_and_drain` — write a steer into a Job's queue with its worker confirmed dead (simulated interruption), then relaunch `task-worker --job-id` on that SAME Job (admitted by the reclaim arm above) — not `resume`, which creates a new Job with its own queue and would never see the file: the drain injects the steer before the first API call (AC bullet 2).
- `test_steer.py::test_crash_mid_drain_injects_once` — use the drain abort point to kill the worker between the transcript flush and the rename (the file is still queued, its id already in the transcript); on the next run the drain moves it to consumed/ without re-injecting. Assert the provider saw the steer exactly once ACROSS both runs — the failure this guards is zero deliveries, where the restarted worker seeds from the transcript incorrectly and the dedupe then swallows a steer that never actually reached the provider (AC bullet 2 — this, not the restart test above, is what exercises the exactly-once claim).
- `test_steer.py::test_same_millisecond_writers_both_survive` — two concurrent `steer` invocations pinned to one epoch-ms by the clock override both land as distinct queue files and both inject; neither overwrites the other.
- `test_steer.py::test_transcript_and_log_stamped` — the transcript's steer entry carries the steer id and timestamp, and the log line carries a timestamp (AC bullet 3 wants both artifacts stamped).
- `test_steer.py::test_finished_refused_unknown_errors` — each terminal status (completed/failed/cancelled) and an effectively-`interrupted` Job → refusal naming resume; unknown id and ambiguous prefix → non-zero exit, clear error; empty message → non-zero exit with nothing written to the queue (AC bullet 4).
- `test_steer.py::test_undelivered_steer_swept_at_exit` — hold the worker at the gate on its final scripted turn, write a steer, release: the Job completes without draining it and the log names that steer id as undelivered, so the accept-versus-terminate race leaves a trace rather than silence.
