# Runtime speaks Anthropic Messages, not OpenAI chat-completions

The original brief asked for a runtime speaking each provider's OpenAI-compatible chat-completions endpoint. We chose the providers' Anthropic-compatible Messages endpoints instead (`api.deepseek.com/anthropic`, `api.xiaomimimo.com/anthropic`, `api.z.ai/api/anthropic`, `api.minimax.io/anthropic`, `api.moonshot.ai/anthropic`): these exact base URLs, model strings (e.g. `deepseek-v4-pro[1m]`), and keys are already proven in daily use by the implement-handoff skill, whereas each provider's chat-completions path, model IDs, and tool-calling quirks were unverified. Provider genericity is preserved — any Anthropic-compatible endpoint works as a Profile — and the official `anthropic` Python SDK replaces hand-rolled wire code.

**Amended 2026-08-01** — Request-prefix byte-stability on this wire format is load-bearing for cost: the Anthropic-compatible providers cache context by exact prefix match (DeepSeek: automatic, 64-token units, cache-hit input billed ~10x cheaper), so the Runtime keeps `system` and `tools` byte-stable for the life of a Job and grows `messages` strictly append-only — retries replay an immutable snapshot, a drained steer rides only the not-yet-sent tail turn, and a resume seeds the prior history verbatim as the prefix. The hit rate is observable: the loop emits one structured `usage` event per completed turn — the provider-reported counters, `cache_read_input_tokens`/`cache_creation_input_tokens` included — to stderr and, through the progress reporter, into the Job log. A resumed Thread preserves this: the new Job's first request replays the source history verbatim as its prefix (Job ids never enter request bytes), so the prior conversation re-bills as cache-hit. The system template leads with the stable instructional body and trails the per-Job `{workspace}`/`{posture}` slots, so same-posture Jobs share the longest possible cross-Job prefix (tools render before system and are posture-filtered, so cross-posture Jobs diverge there regardless). Rejected: `cache_control` breakpoints — DeepSeek ignores them (its caching is automatic), and sending them would vary the request body for nothing.

**Amended 2026-08-01** (reasoning) — A Profile's `request_extras` ride every request through the SDK's `thinking`/`extra_body` kwargs (`extra_body` keys merge into the JSON body ROOT — the wire body carries e.g. `"reasoning_effort"` beside `"model"`, never a literal `"extra_body"` wrapper). Providers return `thinking` blocks (`{type, thinking, signature}`); those persist in the Thread as ordinary history and replay verbatim on every later turn and across resume — never stripped, never filtered (live-verified on all five providers 2026-08-01, thinking replayed byte-for-byte with signatures and accepted). Extras are constant per Job, so request-prefix byte-stability and the cache economics of the amendment above are unaffected WITHIN a Job and across a resume whose resolved Profile is unchanged; an overlay edit to `request_extras` between a source and its resumed Job changes the request and re-keys the provider's cache prefix — the documented cost of re-resolution (cross-ref the ADR 0006 clause). The `anthropic` floor rises to the verified 0.118 — `>=0.37` predates both the `thinking` kwarg on `Messages.stream` and the `thinking_delta`/`signature_delta` stream accumulation this depends on (recorded in ADR 0009). Cross-reference ADR 0006.
